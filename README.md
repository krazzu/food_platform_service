# Поиск поставщиков продуктов питания

B2B-сервис для поиска и сравнения поставщиков продуктов питания. Позволяет находить поставщиков по смыслу запроса («органическое молоко с сертификатами в Сибири»), а не только по точному совпадению ключевых слов.

---

## Идея

Задача — помочь закупщику или ресторатору быстро находить подходящих поставщиков, не обзванивая каталоги вручную. Главная боль таких поисков в том, что у разных поставщиков разные названия для одного и того же товара: «говядина», «мясо КРС», «beef». Обычный текстовый поиск по ключевым словам здесь плохо работает.

Решение — **гибридный поиск**: семантический (понимает смысл запроса) совмещается со структурированным (фильтры по региону, категории, мин. заказу).

---

## Как работает поиск

```
Запрос пользователя
       │
       ├─► Qdrant (векторный поиск) ──────────────────► список id + score
       │   Текст запроса превращается в вектор,          (ранжирование по смыслу)
       │   ищутся ближайшие по косинусному расстоянию
       │
       └─► PostgreSQL (структурные фильтры) ──────────► список id
           Регион, категория, макс. мин. заказ,
           наличие сертификатов
               │
               ▼
       Объединение: семантический ранк — основной,
       структурные фильтры отсекают нерелевантных,
       результаты без семантического попадания
       добавляются в конец со score 0.5
               │
               ▼
       Итоговый список поставщиков с релевантностью
```

Векторный индекс строится один раз при импорте данных. Каждый поставщик представлен как текст: название + описание + категория + регион + сертификаты + условия доставки.

## Стек и почему именно он

### Бэкенд — FastAPI + PostgreSQL

**FastAPI** выбран за нативный async, автоматическую генерацию OpenAPI-схемы и минимальный бойлерплейт. Для I/O-bound сервиса с одновременными запросами к БД и Qdrant async принципиален.

**PostgreSQL** хранит структурированные данные о поставщиках. Реляционная база здесь оправдана: у данных чёткая схема (поставщик → категория → регионы → контакты), нужны жёсткие фильтры с индексами, транзакции при bulk-импорте.

**SQLAlchemy** (async ORM) — стандарт для Python, даёт типобезопасность, миграции через Alembic, удобный query-builder.

### Векторный поиск — Qdrant + fastembed

**Qdrant** — self-hosted векторная база. Выбран потому что:
- поднимается одним Docker-контейнером без GPU
- REST API из коробки
- умеет хранить payload рядом с вектором (не нужно ходить в PostgreSQL за каждым результатом)
- открытый исходный код, нет vendor lock-in

**fastembed** + модель `paraphrase-multilingual-MiniLM-L12-v2` — ONNX-инференс без PyTorch и CUDA. Модель специально обучена для русского языка (multilingual), даёт векторы 384 измерения, работает быстро на CPU. Модель скачивается один раз при сборке Docker-образа.

### Фронтенд — Next.js + Tailwind CSS

**Next.js** даёт готовую структуру проекта, SSR при необходимости, и хорошо работает в standalone-режиме (один `server.js` без node_modules в итоговом образе — лёгкий Docker).

**Tailwind CSS v4** — утилитарные классы позволяют быстро писать UI без отдельных CSS-файлов, вся стилизация прямо в разметке, легко поддерживать.

### Инфраструктура — Docker Compose + GitHub Actions

Всё завёрнуто в Docker: локальная разработка (`docker-compose.yml`) и продакшн (`docker-compose.prod.yml`) идентичны по сервисам, отличаются только источником образов.

**GitHub Actions** собирает образы и пушит в GitHub Container Registry (GHCR), затем деплоит на сервер по SSH. Весь пайплайн в одном файле, секреты хранятся в GitHub.

## Запуск локально

```bash
# 1. Клонировать и поднять все сервисы
docker compose up --build

# 2. Загрузить тестовые данные (232 поставщика)
python3 scripts/import_csv.py scripts/suppliers_template.csv --api-url http://localhost:8000
```

Фронтенд: http://localhost:3000  
API (Swagger): http://localhost:8000/docs

## Деплой на сервер

На сервере в `/opt/food-service/` нужен файл `.env`:

```env
POSTGRES_PASSWORD=your_password
NEXT_PUBLIC_API_URL=http://your-server-ip:8000
```

Пуш в `main` → GitHub Actions соберёт образы и задеплоит автоматически.

Секреты в GitHub Actions (`Settings → Secrets`):
- `SERVER_HOST` — IP сервера
- `SERVER_USER` — пользователь (обычно `root` или `ubuntu`)
- `SERVER_SSH_KEY` — приватный SSH-ключ

## Что можно добавить в следующей итерации

### AI-движок в стиле Perplexity

Сейчас поиск возвращает список карточек. Следующий шаг — сделать так, чтобы система сама отвечала на вопрос: «Кого из этих поставщиков выбрать и почему?»

Схема: запрос пользователя → семантический поиск → топ-N карточек передаются как контекст в LLM (Claude / GPT-4o) → модель формулирует аналитический ответ со ссылками на конкретных поставщиков.

Это именно то, что делает Perplexity: не просто выдаёт ссылки, а синтезирует ответ из найденных источников. Для B2B это особенно ценно — закупщику не нужно читать 20 карточек, он получает сразу сравнение и рекомендацию.

### ELK-стек для аналитики и наблюдаемости

**Elasticsearch** — замена или дополнение к Qdrant для полнотекстового поиска с поддержкой морфологии русского языка (analyzer `russian`). BM25 из коробки даёт хорошее ранжирование для точных совпадений, а гибрид BM25 + векторный поиск (ELSER) — state of the art для retrieval.

**Kibana** — дашборды по поведению пользователей: какие запросы чаще всего не дают результатов, по каким категориям ищут больше всего, в каких регионах дефицит поставщиков. Это прямой сигнал для того, какие данные надо собирать в первую очередь.

**Logstash / Filebeat** — сбор логов из всех контейнеров в единое место, алерты при аномалиях.
